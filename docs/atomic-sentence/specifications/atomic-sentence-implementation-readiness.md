# Atomic Sentence Implementation Readiness

**Status:** Planning assessment only. No implementation or schema change is authorized by this document.  
**Readiness conclusion:** DB-01 is **not ready**. Product decisions and contract conflicts below must be resolved first.

## Current application capabilities and constraints

These findings were checked against the current repository; the proposed architecture and logical data model are not treated as implemented features.

- **Application boundary:** FastAPI routes, page handlers, and the current analysis worker are composed in app.py. The existing workspace is primarily Jinja templates and browser-side JavaScript; React/Vite is used for the Toulmin/AIF graph widgets, not as a separate application.
- **Paper catalog/files:** paper_store.py owns the SQLite store. The papers table is keyed by a column named doi, and analysis accepts DOI values plus SLR work IDs using a slrwork_ prefix. Reuse the existing record key and local valid file rather than assuming every paper has a DOI or making a second catalog.
- **PDF and mapped text:** PDF intake/validation and download are existing workflows. ai_analysis.py obtains document structure through GROBID and creates an adjacent .fulltext.json containing full_text, section hierarchy, exact offsets, page spans where available, and the source PDF SHA-256. The loader validates the mapping against the PDF hash, reconstructed text, and section offsets. There is no Atomic document-version or sentence-index store; the current mapping does not provide a separate Atomic run-level mapping/segmenter snapshot.
- **PDF review:** The current analysis page uses vendored PDF.js, a PDF endpoint, and source highlights. Reuse its patterns and original PDF. GROBID does not provide a configured OCR fallback.
- **AI:** The current analysis path uses configured Ollama/Gemini structured calls and an in-process asyncio queue with one analysis worker. Atomic prompts, schemas, lifecycle, and outputs do not exist. Current provider work can inform reuse, but must not share mutable analysis draft status.
- **Persistence/review:** SQLite uses foreign keys and WAL. Existing tables persist paper-analysis runs, sections, propositions, relations, and review events. The Atomic model should be additive because these objects have different meanings. Review APIs currently use local-user defaults and allow edits to existing analysis objects; they do not establish the trusted individual identity or immutable versioning required by Atomic.
- **Deployment/integration:** Existing Compose configuration includes the app, GROBID, and existing AI/SAFFRON services. The optional SLR System integration handles current paper/analysis contracts; no Atomic destination contract was found.
- **Existing workflows to preserve:** download/search, paper library, RIS export, analysis queue and drafts, GROBID mapping, PDF viewer, Toulmin/AIF, SAFFRON/OpenAlex, review history, and optional SLR sync.

## Decision gates by build order

1. **Owner scope decisions:** approve the required/deferred boundary, language, reviewer policy, role/origin guide, correction flow, SPS handling, evidence-span policy, reported-prior behavior, and stale-source behavior. Record approvals; do not infer approval from this proposal.
2. **Requirements/evaluation package:** finalize the product and annotation contract, lifecycle, evaluation protocol, pilot domain/sample, and target status. Keep the gold-set protocol separate from product reviewer quorum.
3. **DB-01:** prepare and review the additive SQLite persistence/migration plan after those choices are stable. No schema work is included in this QA-02 task.
4. **BE-01 and source readiness:** establish the Atomic route/service boundary and eligibility checks over existing paper/PDF/mapping artifacts.
5. **Source index, then AI-01:** validate exact sentence segmentation/offsets before candidate extraction and atomization. QA-02's stage naming should be reconciled with the earlier implementation plan first.
6. **AI-02:** add source-linked context completion and advisory precheck once versioned evidence and lifecycle rules are stable.
7. **FE-01:** build source-linked human review on top of stable API and candidate contracts; keep the current analysis view and review records separate.
8. **LIB-01:** publish verified-only search and JSON/CSV export only after review, identity, and staleness invariants work end to end.
9. **Regression and pilot:** validate current SLR workflows, run the adjudicated evaluation sample, report metric denominators and known errors, and obtain an explicit release decision.

## Task-ID and readiness conflicts to resolve

- The current implementation plan already labels **QA-02** as “Build adjudicated evaluation set.” This QA-02 request uses the same ID for “Atomic Sentence Product & Research Decision Review.” Resolve backlog IDs before creating implementation tickets.
- The current implementation plan labels **AI-01** as canonical sentence source indexing, **AI-02** as extraction/linguistic annotation, **AI-03** as atomization/context completion, and **AI-04** as precheck. The QA-02 request assigns **AI-01** to extraction/atomization and **AI-02** to context completion/precheck. The stage names in this document follow the QA-02 request, but the project backlog must map IDs to one canonical breakdown.
- The prior architecture proposal describes hedge scope, stance, engagement, and metadiscourse as steps in its proposed pipeline. The QA-02 MVP recommendation defers these separate annotation subsystems while preserving uncertainty semantically. This is a scope refinement requiring owner approval, not evidence that those capabilities exist.
- The repository audit says the Atomic PRD/research pack was not found during the earlier audit. The required PRD and research PDFs are now present in docs/atomic-sentence/research. Do not rewrite the earlier audit in this task; treat that statement as a historical/stale finding.
- The prior logical data model is a proposal and includes versioning/evidence recommendations; no Atomic tables, routes, prompts, sentence index, or library are currently implemented.

## DB-01 readiness decision

**DB-01 is not ready.** It depends on product approval of schema-affecting policies, an accepted MVP scope, resolution of the SPS fallback, and a stable source/reviewer contract. Existing SQLite and paper-store conventions are reusable, but their existence does not settle Atomic semantics. Starting a migration now would encode open requirements or reuse mutable analysis tables with incompatible meanings.

This assessment is not a request to begin DB-01. Work should stop at this readiness proposal until the product owner reviews and records the required decisions.

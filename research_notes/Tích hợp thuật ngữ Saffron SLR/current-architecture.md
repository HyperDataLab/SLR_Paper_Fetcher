# Current architecture: SLR Paper Fetcher, analysis, and term/taxonomy integration

## Where term and taxonomy extraction belongs

### Takeaway
The Fetcher already has a stable PDF → GROBID full-text mapping → analysis pipeline and a project-import path, while SLR-BE owns canonical project papers, metadata, classifications, and paper-pool filters. Keep extraction as a distinct, versioned corpus-analysis artifact (rather than folding it into argument graphs or overwriting author keywords), then make SLR-BE the owner of project-scoped searchable term/taxonomy records and filter APIs.

### Cited Findings
- Fetcher analysis is queued per downloaded valid PDF; its worker calls `ai_analysis.analyze_pdf`, saves the analysis state and draft, and stores argumentation separately — [app.py](../../app.py#L36), [app.py](../../app.py#L698), [ai_analysis.py](../../ai_analysis.py#L3210), [paper_store.py](../../paper_store.py#L87).
- Before analysis, Fetcher extracts via GROBID and maintains a checksum-pinned full-text mapping with sections, page spans, and offsets; its current analysis payload distinguishes author-reported/GROBID-reported keywords from text-extracted candidates, and only displays the reported keyword groups as paper keywords in normalized outline — [ai_analysis.py](../../ai_analysis.py#L471), [ai_analysis.py](../../ai_analysis.py#L1255), [ai_analysis.py](../../ai_analysis.py#L1563), [docs/blueprints/current-analysis-data-inventory.md](../../docs/blueprints/current-analysis-data-inventory.md#L11).
- The Fetcher’s SLR sync sends metadata plus `analysis.json` and `fullTextMapping` as multipart files to `/api/public/projects/{projectId}/analysis-runs`; its repository import path can additionally send the PDF. The metadata payload currently forwards `metadata.keywords` but does not forward a distinct Saffron term/taxonomy result — [app.py](../../app.py#L1374), [app.py](../../app.py#L1448), [public-paper-analysis.routes.ts](../../../slr-system/slr-be/src/modules/paper-analysis/public-paper-analysis.routes.ts#L97).
- SLR-BE stores project paper records and analysis runs under each paper’s `analysisRuns` subcollection; analysis-run artifacts are exposed by dedicated read endpoints. Repository `analysisRunSchema` records artifact manifests for analysis JSON, full-text Markdown/mapping, and source PDF, with run/source/schema/review provenance — [paper-analysis.service.ts](../../../slr-system/slr-be/src/modules/paper-analysis/paper-analysis.service.ts#L256), [paper-analysis.service.ts](../../../slr-system/slr-be/src/modules/paper-analysis/paper-analysis.service.ts#L348), [public-paper-analysis.routes.ts](../../../slr-system/slr-be/src/modules/paper-analysis/public-paper-analysis.routes.ts#L100), [repository-openapi.ts](../../../slr-system/slr-be/src/config/repository-openapi.ts#L160).
- SLR-BE’s paper schema already has `classification.primaryTopicId`, `topicIds`, `subfieldIds`, `fieldIds`, `domainIds`, and `taxonomyVersion`; repository work metadata also has keywords and classification. These are existing canonical metadata/classification slots, not evidence that Saffron terms are already supported — [papers.schemas.ts](../../../slr-system/slr-be/src/modules/papers/papers.schemas.ts#L24), [papers.service.ts](../../../slr-system/slr-be/src/modules/papers/papers.service.ts#L215), [repository-openapi.ts](../../../slr-system/slr-be/src/config/repository-openapi.ts#L150).
- Current paper-pool `keyword` filtering lowercases and substring-matches title, abstract, DOI, and author names; it does not match the `keywords` field. The filter is applied after hydrating the operational paper list in memory — [papers.service.ts](../../../slr-system/slr-be/src/modules/papers/papers.service.ts#L501), [papers.service.ts](../../../slr-system/slr-be/src/modules/papers/papers.service.ts#L523), [papers.service.ts](../../../slr-system/slr-be/src/modules/papers/papers.service.ts#L549).

### Inferences
- Suggested placement: add a separate Saffron extraction job/service at the Fetcher’s document-processing boundary, consuming only a validated, checksum-pinned full-text mapping; send its normalized result as a new versioned artifact through the existing analysis-run upload contract. This reuses current extraction, run identity, artifact storage, and source provenance while keeping Saffron’s corpus-mining output separate from the AI argumentation draft.
- Suggested SLR-BE ownership: persist parsed terms and taxonomy as normalized project-paper analysis data (or indexed materialized records keyed by `paperId`, `runId`, extractor/schema version, term/concept IDs), while retaining the raw Saffron files as immutable run artifacts. Do not put a generated taxonomy into the existing OpenAlex-style topic ID fields unless IDs resolve against that taxonomy’s own registry/version; keep source, score, method, frequency, language, evidence spans, and review status explicit.
- Suggested filter integration: introduce explicit term/concept/taxonomy filter parameters and a backend index/query path over accepted normalized term records. Preserve existing free-text `keyword` semantics or clarify/change it deliberately; the current implementation’s name suggests keyword search but currently only checks bibliographic text.
- Suggested quality gate: reject or quarantine runs with missing/low-coverage body text, unsupported language, empty/invalid candidates, or PDF checksum mismatch; normalize Unicode/case/whitespace and deduplicate within a document while preserving raw surface forms and candidate provenance. Keep candidate, normalized term, consolidated concept, and taxonomy node as distinct entities. Require human approval or a declared quality threshold before using extracted concepts in inclusion/exclusion filters.

### Gaps
- Local code confirms there is no Saffron-specific module, endpoint, result schema, or term/taxonomy filter parameter yet. The exact Saffron 4.0 artifact formats/configuration should be grounded in the separate SAFFRON feature document and official Saffron source before implementation.
- Repository paper-pool filtering currently hydrates and filters the full operational collection in memory; scaling/index design for term filters needs a separate measurement and Firestore-query review.
- This inspection did not validate production deployment topology or whether SAFFRON 4.0 can run as an embedded library/container in the project’s supported runtime.

## Which current analysis flows to reuse or replace

### Takeaway
Reuse the deterministic PDF/GROBID/mapping/checksum and upload/provenance plumbing. Replace the current AI-generated `text_extracted` keyword candidate path for corpus-wide filter terms with Saffron’s term extraction and taxonomy generation; retain AI profile/argument analysis for different user-facing outputs unless a specific Saffron module provides equivalent, schema-compatible functionality.

### Cited Findings
- Fetcher has three separable analysis layers: the RRR paper profile/draft, quote-anchored outline/profile content, and proposition/relation/AIF/Toulmin argumentation; `analyze_pdf` orchestrates them after GROBID extraction — [ai_analysis.py](../../ai_analysis.py#L1271), [ai_analysis.py](../../ai_analysis.py#L1442), [ai_analysis.py](../../ai_analysis.py#L1725), [ai_analysis.py](../../ai_analysis.py#L3176), [ai_analysis.py](../../ai_analysis.py#L3210).
- Existing text-extracted “keywords” are produced by an LLM profile prompt, validated by requiring the normalized candidate string to occur in its source quote, then deduplicated against author/GROBID keywords. They are currently profile/report data, not a term-frequency/concept taxonomy corpus index — [ai_analysis.py](../../ai_analysis.py#L1446), [ai_analysis.py](../../ai_analysis.py#L1458), [ai_analysis.py](../../ai_analysis.py#L1563), [docs/blueprints/current-analysis-data-inventory.md](../../docs/blueprints/current-analysis-data-inventory.md#L16).
- Full-text mapping generation records PDF identity/checksum and structured source sections; argument proposition extraction and graph construction run downstream of that document representation — [ai_analysis.py](../../ai_analysis.py#L3135), [ai_analysis.py](../../ai_analysis.py#L3176), [ai_analysis.py](../../ai_analysis.py#L3189), [paper_store.py](../../paper_store.py#L113).
- SLR-BE already has its own paper AI analysis module for evidence/AIF review and cross-paper relationship analysis, alongside the separate imported analysis-run artifact module. These serve review evidence and imported source runs, respectively — [paper-ai-analysis.service.ts](../../../slr-system/slr-be/src/modules/paper-ai-analysis/paper-ai-analysis.service.ts#L65), [paper-analysis.service.ts](../../../slr-system/slr-be/src/modules/paper-analysis/paper-analysis.service.ts#L69).

### Inferences
- Priority to reuse: Fetcher’s checksum-verified GROBID mapping and section/page provenance; queue/retry/run status; artifact upload; SLR-BE project-paper identity and analysis-run history. These are infrastructure, not extraction semantics.
- Priority to supersede for filter terms: the small AI `text_extracted` keyword list. It is deliberately quote-grounded but is generated as a per-paper profile aid, not a reproducible corpus-wide ranking/consolidation/taxonomy output. Store it as legacy/profile output if needed; do not merge it into Saffron candidates without labeling its distinct extraction method.
- Keep: author keywords and GROBID-reported keywords as separate provenance-bearing metadata; AI summary, outline, Toulmin/AIF and scientific analysis because Saffron’s term/taxonomy modules do not imply replacement of those tasks.
- Add an orchestration stage after mapping validation and before/alongside profile generation: `fulltext_validated → saffron_terms → concept_consolidation → taxonomy (optional) → quality_validation → artifact_upload`. Make module results independently retryable and record Saffron version/config, language, input hash, and completion/error state.

### Gaps
- The precise SAFFRON 4.0 module interfaces and outputs need confirmation against its feature document and upstream source; this note only maps current application integration points.
- No benchmark was run comparing Saffron terms to Fetcher’s current LLM keywords on the same papers. A curated evaluation set is needed before removing the existing field from any UI/API contract.

## Source-of-truth map and integration contract

### Takeaway
The practical integration boundary is Fetcher’s validated full-text mapping and SLR-BE’s existing public analysis-run/artifact ingestion; SLR-BE’s paper-pool filter is the place to expose searchable accepted terms. Treat code and API schemas below as the current sources of truth, with project notes and generated OpenAPI as navigation aids.

### Cited Findings
- Fetcher source map: GROBID/fulltext/profile/argumentation pipeline — [ai_analysis.py](../../ai_analysis.py#L471); worker/analysis endpoints/sync — [app.py](../../app.py#L36), [app.py](../../app.py#L342), [app.py](../../app.py#L1374); local SQLite run and evidence tables — [paper_store.py](../../paper_store.py#L87); output-field inventory — [current-analysis-data-inventory.md](../../docs/blueprints/current-analysis-data-inventory.md).
- SLR-BE source map: Fetcher analysis-run upload routes — [public-paper-analysis.routes.ts](../../../slr-system/slr-be/src/modules/paper-analysis/public-paper-analysis.routes.ts#L97); validation, run persistence and artifact assembly — [paper-analysis.service.ts](../../../slr-system/slr-be/src/modules/paper-analysis/paper-analysis.service.ts#L69); imported repository run storage — [repository-import.service.ts](../../../slr-system/slr-be/src/modules/repository-api/repository-import.service.ts#L190); paper-pool query/filter and metadata hydration — [papers.service.ts](../../../slr-system/slr-be/src/modules/papers/papers.service.ts#L501); keyword query contract — [papers.schemas.ts](../../../slr-system/slr-be/src/modules/papers/papers.schemas.ts#L60).
- SLR-FE consumer map to verify before UI work: paper-pool query keys, service, and hooks can be found under `src/constants/queryKeys.ts`, `src/services`, and `src/hooks`; use existing paper-pool filter UI as the filter-control extension point. No specific frontend component contract was inspected in this task.
- Current state note: `slr-paper-fetcher/overview.md` reports the local analysis and UI architecture but has `last_verified_commit: unverified`; it was treated as an index only and all cited behaviors above were checked against current code — [overview.md](../../../../obsidian/project/projects/slr-paper-fetcher/overview.md).

### Inferences
- Proposed artifact contract (design, not current code): `term-analysis.json` with top-level `schema_version`, `extractor{name,version,config_hash}`, `input{paper_id,run_id,pdf_sha256,mapping_schema_version,language,coverage}`, `terms[]` including stable term/canonical IDs, surface/canonical forms, n-gram/type, score/rank/frequency, source sections/spans, method, provenance, QA/review state; `taxonomy.json` with versioned nodes, parent/child edges, relation type, confidence, evidence term IDs, and provenance. Keep raw Saffron outputs attached for audit/reprocessing.
- Proposed acceptance gates: valid input checksum and full-text coverage; supported language recorded; candidate evidence points to source text; schema and ID uniqueness validation; bounded candidate counts and minimum evidence/frequency; no untraceable taxonomy edge; extraction run reproducibility from artifact plus config/version. Filter by canonical IDs and reviewed/accepted state, not fuzzy matching raw labels at query time.
- Suggested staged delivery: first store artifacts and display/search terms within one project; next add canonicalization/review and taxonomy navigation; finally add indexed multi-select term/topic filters, counts, and AND/OR semantics. This avoids changing inclusion decisions based on unreviewed extractor output.

### Gaps
- A specific SLR-FE filter component and its current API contract were not traced; verify the consuming hook/service before implementation. Backend endpoint and request schemas are the strongest currently verified filter contract.
- Need decide whether terms are shared globally across projects or project-specific. Saffron corpus statistics and taxonomy consolidation may vary by corpus, so project/run scope should be explicit until product requirements settle this.
- The feature note, official Saffron API/source, and exact launch/deployment environment must be checked before deciding whether to deploy Saffron inside Fetcher, as an adjacent worker service, or in SLR-BE. Architectural recommendation here is an independently versioned worker/service boundary, not a verified runtime capability.
